# Rand zkVM M5.3 — the aggregate program and the chain-facing interface Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** M5.2's machine gains its second program — one that verifies **N inner proofs in one rVM execution** — and the chain-facing API the fullnode's aggregation design consumes: `aggregate`, `verify_aggregate`, and the registered aggregate-program digest. The exit test (spec §7): an aggregate of **3 real bundle proofs verifies natively**, a tampered inner proof makes `aggregate` fail, a tampered aggregate fails `verify_aggregate`, and a fullnode-side stub recomputes the public values from the bundles' public fields and matches. The design question this plan answers with measured arithmetic is **N's economics**: at the post-cut 1 968 619 cpu rows per proof, N=2 production is tier 22 at ~95 GB of committed oracle and N=3 is tier 23 at ~127 GB — neither runs on this 48 GB box, and the spec's "no 23" tier ruling collides with the aggregate's purpose. The exit therefore runs as an **N=3 twin at the test profile** (tier 21, ~36 GB oracle, on this box), and production N ≥ 2 is deferred to M5.4's GPU backend, with the machine classes derived below rather than discovered by OOM.

**Architecture:** The aggregate program is **one N-generic program per inner shape**, not N unrolled programs (ruling R1): a counted loop over a runtime `N` read from the witness tape's header, each iteration running the per-proof pipeline of M5.1/M5.2 over that proof's tape region with a fresh challenger — the native batch verifier's per-proof independence, exactly. The tape is `[N, then per proof its fourteen segments in the pinned order]`, consumed sequentially, so no runtime addressing exists anywhere (R2). The public interface is M5.2's amended §4.4: the 4-element **interface digest** (`RVM_PUB_DOMAIN = 17`) over `[inner_vk_digest(4) ‖ N ‖ 34·N]` — accumulated in memory across the loop and digested after it; the chain recomputes the same list from the covered bundles' public fields and compares digests (the cs6 `H_PUB` pattern M5.2 already ships). One program — and one registered digest — per inner shape covers every window size the sealing pipeline produces; the digest's `N` word binds the count. The chain-facing API is spec §6's three functions, amended by M5.2's rulings: the proof's batch public values are always the 4-element digest, the §4.4 list rides as auxiliary data on `AggregateProof`, and the rVM verifier key is `(FriProfile, Program, Tier)` with the key built once at startup into the FIFO cache.

**Tech Stack:** Rust 1.98.1, Plonky3 0.7 exactly as `recursion/Cargo.toml` pins it, `rand_zkvm` as a path dependency (the inner `Proof` type, the bundle fixtures, `Machine::verify` as the native reference). No new external crates, no CUDA (that is M5.4), no `research/` edits.

**Spec:** `docs/superpowers/specs/2026-09-13-zkvm-m5-recursion-vm-design.md` §6 (the chain-facing interface, amended by M5.2's R5/R6 as below), §7 (M5.3's milestone text and exit test), §8 (testing), §11 (the `H_IN` open item — answered in R3), and the M5.2 amendments recorded in its status line. The measured machine: `recursion/docs/01-rvm-machine.md` (the post-cut numbers this plan is written against — every estimate below is derived from them and labelled). The chain-side design: `fullnode/docs/aggregation.md` (the Aggregate action's fields, the sealing pipeline, the fee/subsidy split, the fallback; its §5 open items). The structural template: `docs/superpowers/plans/2026-09-14-zkvm-m5-2.md`. The built crate: `recursion/src/programs/rv32.rs` (the single-proof program), `recursion/src/machine.rs`, `recursion/src/witness.rs`, `recursion/src/shape.rs`.

## Rulings made in this plan

| # | ruling | why (with the arithmetic) | cost if wrong |
|---|---|---|---|
| R1 | **One N-generic aggregate program per inner shape** — a counted loop over a runtime `N` from the tape header, not one unrolled program per `(shape, N)` | One registered digest per inner shape covers every window size the sealing pipeline produces; the interface digest's `N` word binds the actual count (the node recomputes it from `covers.len()`). The per-proof pipeline is the loop body, emitted once, so the *program table* stays ≈ one pipeline (~2 M rows) instead of scaling with N (2^21 vs 2^23 at N=3, −5.6 GB of oracle). The loop's invariant holds structurally: everything long-lived (the vk/shape constants, the tape and interface-list bases, the accumulator) is allocated *before* the loop; every per-iteration handle dies in the body (liveness), and the challenger is rebuilt per iteration. | If the counted-loop replay invariant objects in practice, the fallback is per-`(shape, N)` unrolled builds — one program (and registration) per admitted N — with the Task-2 tasks re-pointed; the N-generic structure is attempted first and the fallback is a documented task, not an improvisation. |
| R2 | **The tape is `[N, proof₀'s 14 segments, …, proof_{N−1}'s]` and is consumed sequentially** — no runtime addressing | Each proof's segments have compile-time lengths (the shape fixes them), so iteration `j`'s region is the next words in order: the program never seeks. The transcript resets per proof — a fresh `DslChallenger` per iteration — because the native verifier runs `verify()` independently per proof; a continuous transcript across proofs would be a *different* protocol than the one being proven. | A seek-based layout would spend rows on address arithmetic for no benefit; a continuous transcript would silently change what "these N proofs verify" means (a new protocol, not the chain's). Both are named here so they are chosen, not drifted into. |
| R3 | **The `H_IN` open item (spec §11) is answered NO — no extra binding** | `H_IN` is `pv::IN0..7`, already one of the 34 public values the interface digest binds per proof, and the fullnode recomputes it from the covered bundles' public fields (which aggregation.md keeps). The bundle's private inputs are committed by the bundle's own salted `H_IN`; the aggregate's binding of the pv list is transitively complete. Binding `H_IN` again would add words and no soundness. | Recording the answer here is what closes the spec's open item without a chain-visible change; a future guest with *different* input-hiding needs reopens it per guest, not per aggregate. |
| R4 | **The exit runs as an N=3 twin at the test profile on this box; production N ≥ 2 is deferred to M5.4's GPU backend** | The N-economics table below: test-profile N=3 is tier 21 (~36 GB oracle, ~32–45 GB peak — this box alone, watchdog-guarded). Production N=2 is tier 22 at ~95 GB oracle (~85–119 GB peak → ≥128 GB machine) and N=3 is tier 23 at ~127 GB (~113–159 GB → ≥160 GB). The fleet's documented big-proof class is ≥64 GB (`research/docs/04-guests.md`); ≥128 GB is nowhere in it. The RV32 CUDA backend already chunks NTT/Merkle onto the device sized by `free_bytes` (`rand-zkvm-cuda/src/gpu/mod.rs`), so M5.4's backend is the honest home for production aggregates — the tier-23 rung is added there, with the GPU memory model measured, not here where the rung exists only to be unreachable. | Pretending the exit fits and jetsamming the box is the tier-18 EVM story again; deriving the requirement and deferring is R10's precedent, applied one tier up. The user-facing flag: spec §7's M5.3 exit is satisfied by the test-profile twin (3 *real* bundle proofs, verified natively); the production-profile aggregate is M5.4's measurement to make. |
| R5 | **The interface digest is M5.2's pinned construction over `[inner_vk_digest(4) ‖ N ‖ 34·N]`, and sealed history must carry each bundle's declared shape** | The construction is `public_digest` (`RVM_PUB_DOMAIN = 17`, capacity header `[domain, len]`, rate-4 absorb) — already the fullnode's `H_PUB` pattern. The `inner_vk_digest` component commits to the *shape* (tier, six declared heights, profile, arity schedule, cap), and those live in the bundle proof's **header**, not in its 34 pv — so aggregation.md's pruning story ("the ~3 KB of public fields per transfer stay") loses them unless it also keeps the 9 bytes of `tier + six heights` per bundle. Admission needs them to recompute the list. **Chain-side correction 1 (user-facing).** | Without the shape on record, sealed history cannot recompute the interface digest and admission is vacuous. Correction 2, same reason: admission must check every covered bundle's declared shape equals the aggregate's shape — one aggregate covers one shape's proofs (the chain's single transfer relation is one shape in practice, but the check is what makes that a fact rather than an assumption). |
| R6 | **The API surface is spec §6's, amended by M5.2's R5/R6** | `AggregateProof { proof: machine::Proof, public: Vec<F> }` — the batch pv are the 4-element digest, `public` is the §4.4 list (auxiliary data, like `verify_public`'s words). `aggregate` shape-checks every inner proof (`InnerShape::matches` → `AggregateError::WrongShape`), builds the tape, proves, and asserts the executed digest equals the host-computed one. `verify_aggregate` = digest check on `public` ↔ batch pv, then `Machine::verify(&program, &proof)`, returning each bundle's `OUT0..7` as `[u32; 8]`. | R7 | **N is measured at both profiles where this box can, derived where it cannot** | The N-economics table below is the deliverable: test profile N=1–3 fully measured (tiers 19/20/21, oracle 10/20/36 GB, the twin runs on this box); production N=1 measured (tier 21, 48.6 GB oracle — the M5.2 exit's own number); production N=2/N=3 **derived** (tier 22/23, ~95/~127 GB), with the exit-twin at N=3 test profile as the in-scope run. `tests/pins.json` gains a per-N record; the budget test asserts the regime (rows = N × per-proof rows + loop overhead, pinned per N). | A guessed N table is how the chain sizes its subsidy wrong; measuring and deriving with the derivation shown is the AGENTS.md rule, applied to the number the chain actually spends against. |

Per-proof scaling is linear: each iteration of the aggregate loop costs one per-proof pipeline, so cpu rows, register accesses, RAM accesses, permutations and reduce rows multiply by N, and the program table holds the one emitted loop body (R1) with the interface-list accumulation added (`34·N` stores + the digest, ≤ a few hundred rows).

**The options, with arithmetic.** (a) Big metal: the N=3 production exit on a ≥ 160 GB machine — no such machine is documented in the fleet (the class is ≥ 64 GB). (b) Defer production N ≥ 2 to M5.4's GPU backend: the RV32 CUDA backend already chunks NTT/Merkle onto the device by reported `free_bytes`, so the rVM backend inherits chunking; host-side state at N=3 is the witness traces (~5.6 GB) plus batch state, and the device's per-chunk need sizes to the board. (c) Further row cuts first: the remaining per-proof terms are tape reads (~400 k, a `HINT4` at ~−150 k), Merkle-walk bit-selects (~136 k, a `MERKLE` select-compress at ~−100 k), `sample_bits` (~94 k, `EXPBITS` — already rejected at ~3 %), folds (~100 k, `FRIFOLD` — already rejected): a full new menu ≈ −22 %/proof → N=3 at ~4.6 M rows, **still tier 23** (needs −29 % for tier 22) and the table heights barely move (they are powers of two) — a new chip family, an ISA change and a differential suite to buy nothing that changes the machine class. **Recommendation: (b)** — R4 as ruled; (c) is recorded with its arithmetic so the rejection is a decision, not an oversight; (a) is recorded as unavailable.

## The aggregate program's structure (what Task 2 builds)

**The tape** (Task 1): one flat `Vec<F>` the program consumes with `HINT` in order —

```
[0]                       N                              (one word; the program pins it as the loop count)
[1 .. 1 + L)              proof 0's fourteen segments, in the M5.1 pinned order and lengths
[1 + L .. 1 + 2L)         proof 1's fourteen segments
…                          (L = Σ segment lengths, a compile-time function of the shape)
[1 + (N−1)L .. 1 + NL)    proof N−1's fourteen segments
```

The per-proof region is the M5.1 tape verbatim, so the tamper tests index it as `(proof j, segment)` with the same refusal-step table, and the witness builder reuses `WitnessTape`'s per-proof writer unchanged, once per proof, appending.

**The program** (Task 2): shape-specialized per `InnerShape` exactly as the single-proof program is (the shape words, the `InnerKey` cap, the FRI schedule are compile-time constants), and then:

1. read `N` from the tape's first word; pin `1 ≤ N` (a zero count traps at a named checkpoint — the build-time `MAX_N` is only a memory bound, not a protocol constant);
2. allocate the interface list's base (`4 + 1 + 34·N` cells — a runtime bound: allocated as `4 + 1 + 34·N_max` would bake a cap in, so the list is built by **append-offset arithmetic** at `[vk(4) ‖ N ‖ …]` with the per-proof cursor advanced per iteration — no `N_max` exists anywhere);
3. the counted loop, `j = N … 1`: per iteration, a fresh `DslChallenger`, then the M5.1/M5.2 pipeline over this iteration's tape region in the pinned order — header (the proof's declared shape pinned against the program's, so a wrong-shape proof is refused at its first header word), transcript and commitments, the lookup-terminal sum, phase-5 constraint evaluation at `zeta`, the phase-6 preamble, the four query-major segment reads, the unrolled query loop (Merkle walks, the `REDUCE` runs, the folds), and the §4.4 accumulation: the iteration's 34 inner public values stored into the interface list at its cursor;
4. after the loop: the `inner_vk_digest` recomputed once from the compile-time shape words and cap (as today), stored into the list's first four cells; `N` stored in the fifth; then the interface digest — `hash::sponge_seeded(b, RVM_PUB_DOMAIN, list, 4 + 1 + 34·N)` with the block count from the runtime `N` — and the four digest lanes `PUBLIC`ed.

Every per-proof value the M5.1 differential suite pins (challenges, fold values, the accumulator, the quotient identity, the refusal steps) flows identically per iteration; the suite reruns on the looped program (Task 2's differential), so a divergence in the loop is caught by the same named checkpoints, not by a new oracle.

**The interface digest** (R7): exactly M5.2's construction, `public_digest` over `[inner_vk_digest(4) ‖ N ‖ 34·N]` with `N` as one field element — absorb order pinned by test: vk digest, then the count, then the proofs' 34 pv each in tape order. The host's `interface_words` gains the N-ary form (`interface_words_n(shape, key, pvs: &[Vec<u64>]`) beside the N=1 form, and the program's phase 8 (after the loop) and the host helper are pinned to each other on every fixture set.

**The digest the fullnode registers**: `aggregate_program_digest(shape) = the N-generic program's digest` — one per inner shape (R1), built deterministically from `(InnerShape, InnerKey)` like the single-proof build, with a test that rebuilding reproduces it.

**The stub, exactly** (a new, small fullnode-side function — no rVM vendoring in M5.3):

1. Input: an aggregate transaction (`Aggregate { covers, proof, payout, r }`), the covered bundles' records, and the node's registered aggregate-program digest.
2. For every covered bundle: read its declared shape (`tier` plus the six declared log-heights — **R5's correction 1: sealed history must carry these 9 bytes per bundle, or the stub cannot run**), and check it equals the aggregate's shape (**correction 2**).
3. Compute `InnerShape`-equivalent words from the shape (the `shape_words` layout in `recursion/src/shape.rs`), the inner cap from `Machine::verifier_key(tier, the six heights)`, then `inner_vk_digest` = `PaddingFreeSponge<Perm, 8, 4, 4>` over `[RVM_VK_DOMAIN = 16 ‖ shape words ‖ cap(16)]`.
4. Build the interface list: `[inner_vk_digest(4) ‖ covers.len() ‖ per bundle its 34 pv in cover order]`, and `public_digest` over it: state `[0,0,0,0, RVM_PUB_DOMAIN = 17, len, 0, 0]`, then one permutation per four words overwriting rate lanes 0..4 (partial trailing block overwrites only its own lanes), digest = lanes 0..4.
5. Compare the four words with the aggregate proof's batch public values; mismatch → the aggregate is invalid. Then the ordinary rVM `Machine::verify(&registered_program, proof)`.
