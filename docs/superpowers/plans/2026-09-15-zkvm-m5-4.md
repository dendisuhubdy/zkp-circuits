## What M5.3 hands M5.4

- **The pinned aggregate program and its digest** — one N-generic program per inner shape
  (`recursion/src/programs/rv32n.rs`): a counted loop over the tape's `N`, the interface digest
  over `[inner_vk_digest ‖ N ‖ 34·N]`, one registered `Program::digest` per shape. The M5.4
  self-verifier reads it the way the aggregate program reads the RV32 machine's shape.
- **The measured N-economics.** Test profile (pinned in `recursion/tests/pins.json`): N=1
  441 782 rows / tier 19, N=2 883 240 / tier 20, N=3 1 324 694 / tier 21; the closed model
  `rows(N) = 328 + N·441 454 + 4·⌊N/2⌋`; witness tape `1 + 43 344·N` words; the program is
  443 893 instructions, independent of N. Production: N=1 measured 1 968 758 rows (the M5.2 pin
  plus the same 139-row loop overhead); N=2 tier 22 at ~95.3 GB oracle (≥ 128 GB host), N=3
  tier 23 at ~127 GB oracle (≥ 160 GB host) — and tier 23 is **not a rung today**
  (`recursion/src/machine.rs`'s `TIERS` stops at 22; `Tier::for_cycles` returns `NoTier`).
- **The chain-facing API, settled** — `aggregate` / `verify_aggregate` / `aggregate_program` /
  `aggregate_program_digest` (`recursion/src/aggregate.rs`), the fullnode admission stub's
  five-step spec and test vectors (`recursion/docs/02-aggregate.md`), and the startup key-build
  story (18.31 s measured at 2^19; the 2^21 production build estimated ~30–70 s).
- **The 2026-09-15 ruling** — production-profile proofs (M5.2's tier-21 exit, N≥2 production)
  are *written* now and will be *executed on a ≥ 64 GB machine after chain-side aggregation
  lands*. Chain-side aggregation itself is approved design, not built
  (`fullnode/docs/aggregation.md`).
- **The deferred-run inventory** — the M5.3 exit's honest state: N=1 tier 19 completed (three
  runs; 328 121-byte proof; 30 GB sampled peak; ~27–30 min wall); N=2 tier 20 and N=3 tier 21
  jetsam'd on the shared dev box (SIGKILL at 33.7/33.3/31.5 GB sampled; the box's practical
  line that day was ~30–33 GB), `#[ignore]`d with their run-alone command lines.

## Global constraints

1. **TDD, all green before every commit**, the M5.2/M5.3 rhythm: failing tests first, then the
   implementation, then the full suite, then the commit.
2. **Differential everything.** The rVM's rule stands: the emulator is the reference semantics;
   every backend/engine claim is pinned against the CPU verifier on *real* proofs (the disk-cached
   fixture family), never against a second implementation of the same idea.
3. **The backend must not change the proof.** A CUDA-produced proof verifies on the stock CPU
   `Machine::verify` unchanged — `research`'s own discipline, already built there, mirrored here
   exactly. No fallback either: if the GPU path cannot start, the call errors and nothing is
   produced (the fullnode's `--cuda` ruling applies to the rVM identically).
4. **Measured numbers in the docs** (`AGENTS.md` rule): the device model, the tier-23 rung, the
   N re-measurement, the self-verifier's rows and its machine class — measured where the plan
   says measured, labelled `derived` where it is arithmetic from measured inputs.
5. **No cargo on the dev box while a watchdog-guarded proof is running** — the heavy runs are
   scheduled, not opportunistic (the M5.3 jetsam lessons: the shared 48 GB box kills the largest
   process at ~30–33 GB under pressure).
6. **`research/` is frozen** — the backend is a *config* concern; the RV32 machine does not
   change. `rand-zkvm-cuda/` changes are test-facing only (the mock driver's `free_bytes`), and
   the kernel crate `gpu-kernels/` changes only if the PTX bring-up (T3) forces it.

## Rulings

**R1 — the backend is config-level; no new kernels.** The rVM shares with the RV32 machine the
exact things the kernels touch: Goldilocks, `Poseidon2Goldilocks<8>` with the `PERM_SEED`
constants (`rand_zkvm::tables::poseidon2` is re-exported by the rVM's poseidon2 table), the
two-level twiddle table to 2^26 (`LOG_MAX = 26` covers the rVM's largest LDE, tier 23 cpu at
2^26), and the hiding-FRI shape (log_blowup 3, max arity 3, cap height 2, salting stream). The
backend's own arithmetic is dimension-only: `Dft<E>` chunks columns of any matrix, the Merkle
engines hash rows of any width. So `rand-zkvm-cuda`'s ten kernels
(`to_col_major`/`to_row_major`, `bit_reverse`, `zero_extend`, `scale_pow`, `dif_stage`,
`dif_tiles`, `copy_columns`, `poseidon2_rows`/`compress`/`inject`) cover the rVM's eight
instances — program, cpu, reg/ram memory, poseidon2 (permutation-per-row with the SPONGE kind),
public, range, reduce — with **zero kernel work**. What the rVM adds is research's backend
split, mirrored: a `Backend` enum, `reference_cfg` and `cuda_cfg` modules, `prove_with` and a
generic `prove_on` (`recursion/src/machine.rs`), and the feature trio
`reference-backend` / `mock-cuda` / `cuda` in `recursion/Cargo.toml` pointing at
`../rand-zkvm-cuda` exactly as `research/Cargo.toml` does. Reuse by phase: NTT — the crate's
`Dft<E>` unchanged; Merkle/cap — `HidingMmcs<E>` unchanged (its verifier side already delegates
to Plonky3's `MerkleTreeHidingMmcs`, so *verification stays CPU regardless of backend*);
quotient — host-side by construction in both machines (the quotient chunks are evaluated
host-side and only committed, so there is nothing to port); FRI — the commit/open path is the
same `HidingFriPcs` over the same MMCS, so it rides the same engines.

**R2 — determinism is research's postcard discipline, mirrored.** `research::prove_on` proves
the batch on the alternative config, serialises it, and decodes it as the CPU `Config`'s
`BatchProof` — same permutation, same salt stream, same FRI parameters, so the wire encoding is
a pure retyping and the CPU verifier accepts it. The rVM's `prove_on` duplicates
`recursion::machine::prove_traces`'s body under that same rule, with the same "change one,
change the other" comment research carries. The equivalence *tests* mirror
`fullnode/crates/shrugg-zkvm/tests/backend.rs`: every rVM program with a fixture tape (the
single-proof verifier and the N-generic aggregate, at the test profile) proves on
`Backend::Reference` and on `Backend::Cuda`-with-mock-driver, verifies on the stock CPU
verifier before and after a `to_bytes` round trip, and a shape test asserts the two proofs nest
identically (same tier, same public values, same commitment presence, same per-instance opened
run lengths; sizes within a salt-driven factor, not a bound). The deterministic key split is
already the rVM's: `key_config`'s `KEY_SEED`-seeded RNGs, which the backend configs reproduce
exactly or the preprocessed cap diverges.

**R3 — the device-memory model; the host is unchanged.** The backend accelerates NTT and Merkle
*compute*; it does not shrink host memory — traces, salted matrices, and digest layers live on
the host in `ProverData` exactly as on the CPU path. The machine classes from M5.3 therefore
stand: tier 21 → ≥ 64 GB, tier 22 → ≥ 128 GB, tier 23 → ≥ 160 GB. The *device* model, from the
backend's own chunking arithmetic:

- NTT: `max_columns(n) = (free_bytes / 2) / (n · 8 · 4)` columns per chunk (the engine's own
  rule — LDE keeps ~4 buffers of `n×wc` alive; the ½ is headroom). At the LDE height of a tier's
  cpu trace (2^(t+3), blowup 3): an 80 GB card chunks tier 23's cpu trace (2^26 rows) at ~74
  columns per pass — one pass for its 66 columns; a 40 GB card at ~37 columns — two passes.
- Merkle: the engines upload whole (salted) matrices at once, guarded by `free_bytes`. The
  dominant upload is the cpu LDE matrix at 70 salted columns: 2^24 × 70 × 8 B = **9.4 GB at
  tier 21**, **18.8 GB at 22**, **37.6 GB at 23**. With its digest layers (~2× 32 B per leaf row:
  ~1.1 / 2.1 / 4.3 GB) and the NTT chunk buffers, the device peaks at roughly **12 / 24 / 45 GB**.
  Poseidon2 (production N=3: ~155 k permutations → 2^18 rows, LDE 2^21 × 345 salted × 8 ≈
  5.8 GB) and the memories (2^23 → LDE 2^26 × 15 salted × 8 ≈ 8 GB each at tier 23) are under
  the cpu matrix every time.

So: **an 80 GB device class (H100, A100-80G) runs every tier through 23 unchunked**; a 40 GB
card runs tiers ≤ 22 and tier 23 only with the R3-stretch below. The stretch: **chunk the Merkle
leaf upload by rows** — `poseidon2_rows` is row-independent and the openings are computed
host-side from `originals` anyway, so the leaf layer can stream (upload a row slice, hash,
download digests, reuse the buffer) with no new kernel and no ABI change. It is a stretch, not
a dependency: the plan targets the 80 GB class and takes the stretch only if the provisioned
node is smaller.

**R4 — the tier-23 rung is added with the backend, not before.** `TIERS` gains 23 in the same
change that lands the device-model table (T2), because the rung is meaningless without a
machine that can run it: host ≥ 160 GB (M5.3's derived ~127 GB oracle), device 80 GB class
(R3). The test that pins it is the rung's presence plus `Tier::for_cycles(5 905 862) ==
Some(Tier(23))` — the production N=3 row count, derived from the measured model — not a proof.

**R5 — N re-measured at production, on the GPU node, as measurement.** The 2026-09-15 ruling
sequences the chain's production proofs after chain-side aggregation lands on a ≥ 64 GB
machine; M5.4's re-measurement is *not* a chain proof — it produces the numbers the chain's
configuration (N, slot budget, subsidy) will be set from, so it runs as soon as the GPU node
exists, and the docs label it measurement. The matrix: test profile N=1..3 for software
bring-up (small, fast, the same programs the dev box emulated), then production N=1/2/3 at
tiers 21/22/23 (48.6 / ~95 / ~127 GB host oracle — the node's host RAM must cover the run it
executes; the ≥ 160 GB host covers all three). Each run records prove wall time, verify time,
proof size, device peak, host peak — M5.3's table completed with GPU numbers beside the CPU
ones. The CPU measurements of the same shapes stay in the big-machine runbook (appendix A) as
the baseline the GPU numbers are reported against.

**R6 — the self-verifier's feasibility verdict: deferred, with the requirement measured.** The
self-verifier program (§4.5) verifies one rVM proof; its cost is the same replay of
`verify_batch`, specialised to the rVM's own batch shape (7–8 instances: program, cpu, reg,
ram, poseidon2, public, range, reduce-optional) at the rVM's own FRI parameters (blowup 3,
arity ≤ 3, queries by profile). The derivation from measured inputs: the FRI phase dominates the
verifier program (~60% of rows, M5.1/M5.2's measurement) and scales with opened columns per
query. The RV32 shape opens ~640 (the 01-rvm-machine.md proof-size figure); the rVM shape opens
*more*, because the poseidon2 chip alone is 341 columns — widths sum to ~466 base columns
(program 3+4, cpu 66, memories 11+11, poseidon2 341, public 7, range 1+1, reduce 21) before
next-row, quotient, random, and permutation extension runs, for an estimated ~800–1 100 opened
columns per query. Scaled against the M5.2 exit's measured 1 968 619 rows at ~640 columns:
**the self-verifier over a production-profile rVM proof is an estimated 2.6–3.5 M rows → tier
22** (2^22 = 4.19 M), oracle in the ~97–130 GB class → **a ≥ 128 GB machine**; over a
test-profile proof (16 queries) an estimated 1.2–1.5 M rows → tier 21, ~50–60 GB. **Verdict:
the end-to-end self proof does not fit the dev laptop; it is deferred with the measured
requirement, exactly the path spec §7 allows — and the requirement is *measured* in T6 by
emulation (the laptop builds the program and runs the tape; no proving), replacing this
derivation with a number before the runbook entry is final.**

**R7 — the self-verifier is a sibling shape, not a generalisation.** `InnerShape`,
`reference::replay`, and `witness::WitnessTape` are RV32-proof-specific (six declared heights,
research's `chips()`, research's `Proof`). The rVM's own proof carries a different header
(tier, reg, ram, poseidon2, reduce — five values, the program height implicit in the committed
program, public fixed at 8, range fixed at 256). Rather than generalise `InnerShape` into an
abstraction with one user of each kind, M5.4 writes the sibling triple — `shape::RvmShape` +
`RvmKey`, `rvm_reference::replay`, `witness::RvmWitnessTape` — mirroring the RV32 triple's
structure and pinning rules, and `programs/rv32r.rs` reusing *the same* phase machinery where
it is already generic: `constraints.rs`'s `Emit` walks any AIR's `SymbolicExpression` DAG, so
phase 5 is driven over `recursion::machine::chips(...)` the way `shape_airs` drives research's.
The tamper discipline is M5.1's verbatim: per-segment tape tampers refused at named steps, plus
the wrong-shape refusal at the header.

**R8 — execution locations, stated plainly.** The dev box (Apple silicon, 48 GB, no NVIDIA
GPU) runs: all DSL/program work, the mock-driver and reference-backend suites, every emulation
(including the self-verifier's measurement), and all docs. `rand-zkvm-cuda/ptx/PTX_BUILD.md` is
the hardware runbook and it is explicit: **no PTX has ever been built — the author's machines
have no NVIDIA GPU and no CUDA 13 toolkit** — so T3/T4 execute on a **fleet GPU node to be
provisioned** (Linux, R580+ driver, CUDA 13, LLVM 21, the pinned nightly, sm_80-class or newer;
80 GB device class per R3; ≥ 160 GB host RAM per R5). No such node is named in any repo today;
the plan marks T3/T4 **blocked-on-provisioning** with the exact specification above, and
everything that can be done without it (T1, T2, T5, T6, T7's docs) is done first, on the dev
box. The ≥ 64 GB CPU machine of the 2026-09-15 ruling is a *separate* requirement: it clears
the CPU batch in appendix A after chain-side aggregation lands.
